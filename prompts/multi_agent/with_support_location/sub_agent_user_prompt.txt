# Task Instructions

## Overview
You are exploring a specific file entry point to find two types of locations related to the reported issue:
- **Edit locations**: functions/methods that the fix directly modifies — these contain the buggy logic or are the primary targets of the code change.
- **Support locations**: functions/methods that are NOT directly edited but are essential for understanding WHY the edit locations need to change (e.g., callers of the buggy function, base classes, related utilities that define key data structures or constants).

Use tools to inspect code, trace call relationships, and classify each finding into the correct category.
You are NOT limited to the entry file — follow promising leads across files.
Final locations must be at function-level granularity: a module-level function or a class method.

For each response:

1. Include a `<think>` section explaining your reasoning and what you are trying to accomplish.
2. If you still need more information, provide one or more `<tool_call>` blocks to execute.
3. If you are ready to finish, provide a `<result>` block and also include an `exit()` tool call in the same response.

## Recommended Workflow
1. Start by examining the entry file: use `get_file_functions` and `get_file_classes` to understand its structure.
2. Based on the issue description, identify which functions/classes look suspicious.
3. Use `get_code_of_function` or `get_code_of_class_method` to inspect suspicious code in detail.
4. Use `get_callers` and `get_callees` to trace call relationships:
   - Functions that contain the buggy logic → **edit locations**
   - Callers or related utilities that clarify the context but don't need changing → **support locations**
5. Follow promising leads across files until you have a clear picture of both types.
6. When confident, return the final result with both lists. If nothing is suspicious, return empty lists.

## Classification Guide

Ask yourself for each candidate location:
- **Would the fix require changing this function's code?** → Edit location
- **Does reading this function help understand the bug, but the function itself stays unchanged?** → Support location

Typical edit locations:
- The function implementing the incorrect behavior described in the PR
- A helper called by the buggy function that also needs updating
- An `__init__` or configuration method that sets a wrong default

Typical support locations:
- Callers that trigger the buggy function (help understand the call context)
- Base classes or interfaces that define the contract being violated
- Related utilities or constants that the edit locations depend on

<IMPORTANT>
- Focus on functions/methods that are MOST related to the issue symptoms.
- When you find a location, clearly classify it as edit or support and explain why.
- Do not explore endlessly — be efficient and focused.
- You MUST return at least 3 edit locations and at least 3 support locations. Explore broadly enough to find both.
- The final response must include both the `<result>` block and the `exit()` tool call.
- If no relevant location exists for a category, return an empty list for that category.
</IMPORTANT>
